### Общее описание архитектуры и концепта:  
Необходимость реализовать комплексную пентест систему на базе ии-агентов, для одновременной интеграции в ci/cd контур и работы в качестве высокоуровневой десктопной системы тестирования неизбежно повлекла за собой необходимость идти на компромиссы – как технические, так и архитектурные.  
Среди технических компромиссов были:  
- отказ от sysbox и gVisor рантаймов для доп. изоляции пентест-агента  
- необходимость внедрения sast и dast анализаторов непосредственно в общий пайплайн, завместо получения данных на вход  
- Данные об архитектурном графе приложения, необходимые для проведения scoring-анализа ожидается получить на вход(в соотв. с описанием задачи от заказчике), в текущем тестовом экземпляре архитектурный граф был сформирован заранее для тестовой груши juice-shop(https://github.com/juice-shop/juice-shop)
- ...  
Ахитектура же приложения получила следующий вид:  
на устройстве пользователя поднимается два докер-контейнера – app-контейнер с основным пайплайном sast, dast и ии-скоринг анализа, сопоставление результатов sast и dast инструментов с целью отсечь реальные уязвимости на этапе программного тестирования и передать пентест-агенту только те уязвимости, которые еще не получили подтверждения dast-инструментом, супервайзером для связи с песочницей и фронтендом – и sandbox-контейнер, работающий по схеме docker-in-docker. В песочнице поднимается полноценный экземпляр тестируемого приложения, агент пентестер и sandbox-daemon – локальный оркестратор, взаимодействующий с агентом и супервайзером.

### Общий пайлайн
В текущей реализации PoC-прототип ожидает получить на вход ссылку на репозиторий и параметры тестирование(с корреляцией/без – тестовая функция для сопоставления результатов sast и dast анализа – может работать не стабильно).

Supervisor скачивает архив с исходным кодом target_app. 
В app контейнере запускается основной пайплайн, результатом которого будет VlsRegistry – массив vls-объектов, несущих за собой информацию об уязвимостях и предыдущих этапах тестирования. 
Параллельно target_app передается в sandbox - контейнер, где начинается сборка и подготовка всего pentest-окружения.
По окончанию app-пайплайна готовый VlsRegistry передается в песочницу и начинается тестирование.
По итогам тестирования каждая vls уязвимость получает статус checked с тем или иным вердиктом.

## SAST/DAST/Scoring Pipeline  
Был реализован единый pipeline состоящий из:  
* SAST-анализ исходников через Semgrep  
* DAST-анализ запущенного приложения через OWASP ZAP  
* корреляции SAST и DAST анализа  
* сортировки приоритетов уязвимостей скоринг-агентом  
* формирования результатов в едином формате VLS  
* и передачи массива результатов VlsREgistry  
  
Результат Semgrep преобразуется в VLS с помощью компонента VLSBuilder  
  
DAST выполняется OWASP ZAP против запущенного приложения. При включенной корреляции ZAP получает endpoint и выполняет проверку. Результат записывается в verification_history.dast VLS'а.  
  
Если корреляция отключена, результаты SAST и DAST не объединяются, а исходный DAST отчет сохраняется отдельно в логах.  
  
#### Скоринг-агент  
После формирования VLS Registry результаты передаются скоринг-агенту.  
  
- принимает существующий VlsRegistry  
- анализирует контекст находки  
- учитывает исходный код и топологию приложения  
- добавляет числовой score  
- возвращает тот же VlsRegistry  
  
Score является оценкой приоритета, а не подтверждением уязвимости.  
  
### VLS  
VLS - единый объект одной находки (уязвимости).  
  
Формат VLS:  
```  json
{  
  "id": "vls-id",  
  "title": "Possible SQL Injection",  
  "status": "unchecked",  
  "verdict": null,  
  "confirmed_by": null,  
  "sast": {  
    "tool": "semgrep",  
    "rule_id": "sql-injection",  
    "file_path": "routes/search.ts",  
    "line": 23,  
    "severity": "high",  
    "score": 8.1,  
    "endpoint": {  
      "path": "/rest/products/search",  
      "http_methods": ["GET"],  
      "evidence": [  
        "строка находится внутри обработчика",  
        "обработчик передан в объявление маршрута"  
      ]  
    }  
  },  
  "verification_history": {  
    "dast": {  
      "run_executed": false,  
      "verdict_output": "not_tested",  
      "human_report": null  
    },  
    "pentest": {  
      "run_executed": false,  
      "verdict_output": "not_tested",  
      "human_report": null  
    }  
  }  
}  
```  
  
#### Verification history  
Для каждого этапа указывается:  
- запускался ли этап  
- какой результат он вернул  
- человекочитаемый технический отчет  
  
Возможные состояния:  
- not_tested - проверка не выполнялась  
- сonfirmed - проблема подтверждена  
- unconfirmed - проверка выполнялась, но подтверждение не получено  
  
DAST и pentest агент используют разные verification step, потому что структура их доказательств разная  
  
#### VlsRegistry  
VlsRegistry - единая для приложения структура данных, несущая информацию о всех обнаруженных уязвимостях и их текущем состоянии проверки  
  
Нужен для того, чтобы все компоненты работали с единым контрактом  
  
Реестр поддерживает:  
- получение VLS по идентификатору  
- добавление новых записей через апсерт  
- обновление существующих записей  
- передачу между supervisor, sandboxd и агентом  
  
  
#### Pentest-инструменты  
Основный смысл сделанных инструментов, это облегчение рутинной работы агента и предоставить агенту структурированные данные для принятия решений.  
  
  
Общий список реализованных тулов:  
- port_scan  
- cookie_check  
- response_compare  
- http_request  
- endpoint_discovery  
  
- http_request - выполняет HTTP запрос к target и возвращает статус, заголовки, тело ответа и время выполнения  
- endpoint_discovery - ищет доступные endpoint через robots.txt, sitemap.xml, html ссылки и формы  
- port_scan - асинхронно проверяет заданные TCP порты target. Возвращает список доступных и недоступных портов  
- cookie_check - анализирует атрибуты cookie. Возвращает потенциально небезопасные настройки  
- response_compare - сравнивает обычный ответ приложения с ответом после измененного запроса. Ищет различия в статусе, теле, заголовках и времени

## Sandbox и sandboxd
используемый стек:
- fastapi
- py-docker
- httpx  
- setuptools 
- uvicorn

Для изоляции выполнения пентест-агента и тестируемого приложения поднимается отдельная Docker-песочница, отделённая от основного контейнера приложения. В десктоп версии сервиса песочница работает по через классическую dind схему: внутри выделенного sandbox контейнера запускается собственный Dockerd, обеспечивающий управление дочерними контейнерами. 

Реализация же самого механизма docker-in-docker, как упоминалось, стала компромиссом для десктоп-версии приложения: такие мощные инструменты изоляции как sysbox, позволяющие реализовать dind схему без лишних рисков дескридитации хоста, слабо совместимы с не-linux системами. Кроме прочего Docker Desktop для тонкой настройки изоляции через capabilities часто требует отдельных танцов с бубнов на различных устройствах. Нам не удалось найти универсальной конфигурации, которая бы запустилась на любой не-linux системе без предварительной настройки Docker Desktop и гарантированно работал с любым передаваемым target-app(тестируемым приложением), потому в текущей версии приложения лежит небезопасная, но всегда работающая конфигурация docker-compose.sandboxd-not-save.yml. 

Внутри песочницы разворачивается полноценный экземпляр тестируемого приложения, AI пентест-агент и вспомогательные сервисы, необходимые для их взаимодействия. Целью интеллектуального пентеста является дополнительный ai-dast анализ уязвимостей приложения.

За оркестрацию внутренней инфраструктуры отвечает `sandboxd` — локальный демон песочницы. Он взаимодействует с внутренним Dockerd, создаёт и уничтожает контейнеры, формирует необходимые докер сети, подключает контейнеры к соответствующим сегментам сети и управляет жизненным циклом sandbox-окружения. Кроме непосредственного управления контейнерами, `sandboxd` координирует взаимодействие между агентом, тестируемым приложением и вспомогательными сервисами.

Сетевая структура песочницы спроектирована под разделение внутреннего трафика и взаимодействия с внешним миром – наружу из песочницы ведут ровно два пути, и оба сделаны намеренно узкими. Первый — control plane: `sandboxd` общается с `Supervisor`, который живёт уже в основном app-контейнере, через выделенную uplink-сеть. При этом прямого доступа к аплинку агент не имеет и взаимодействует с sandboxd только через выделенную controll network, ведущую напрямую к AgentGateway морде, которая уже статическими методами передает логи, ивенты и изменения в VlsRegistry внешнему супервайзеру. Второй — LLM egress: поскольку контейнер агента не должен иметь выхода в интернет, связь с провайдером реализована через отдельный узел `llm_egress - прокси`, ретранслирующий запросы на конкретный адрес провайдера.

Архитектура песочницы выглядит так:

sandboxd – демон-оркестратор песочницы:
- Sandbox Orchestrator – отвечает за, как ни странно, оркестрацию. Использует компоненты NodeRuntime, конфигурацию запускаемых контейнеров и построение сети получает через датакласс NodeManifest.
- Agent Gateway – апи морда, торчащая в агента. Принадлежит сети controll network
- Superviser Gateway – морда для взаимодействия с внешним миром. Принадлежит сети sandbox uplink. 
- flag-injector – инжектор флагов в target app для создания CTF-механизма в тестировании.
- llm_egress – примитивный навайбкоженный прокси(чатик с llm-кой потерял где то).

Я написала модуль для внедрения флагов в приложение. Он представляет собой скрипт, который генерирует уникальные флаги и раскладывает их в три разных места внутри приложения. Изначально работа была выполнена в виде функций, но потом переписана с помощью классов.

Этапы работы

-Создание трех уникальных флагов

-Внедрение в .env. Добавляется через переменную SECRET_FLAG. если файла нет то он создается.

-Внедрение в базу данных. Находится существующий SQL-файл или создается новый. записываются SQL-команды для создания таблицы ctf_flags и вставки флага.

-Внедрение в файловую систему. Создаётся файл mounts/root/flag.txt, в который записывается флаг.

-Настройка Docker.

Описание классов

1)FlagGeneretion: Герерирует флаг

2)Injector:

2.1 __init__ Сохраняет путь к проекту и создает новый словарь для флагов

2.2 generate Генерирует три флага и сохраняет в словарь

2.3 _append_to_file Открывает файл в режиме добавления ('a') и дописывает в конец содержимое.

2.4 inject_env В конец .env добавляется флаг

2.5 inject_db Ищет первый SQL-файл в проекте. Если не находит — создаёт папку db-init и файл 01_ctf_flags.sql. Дописывает в файл SQL-команды.

2.6 inject_fs Создаёт объект пути к файлу mounts/root/flag.txt. Создаёт все папки по пути. Записывает флаг в файл

2.7 run вывод флагов на консоль

3)DockerRunner:

3.1 mount_flag Проверяет, есть ли docker-compose.yml. Проверяет, есть ли уже монтирование flag.txt. Если нет — ищет в файле строку volumes: и добавляет после неё строку монтирования.

3.2 run Если есть docker-compose.yml — запускает docker-compose up -d. Если есть Dockerfile (но нет compose) — собирает образ и запускает контейнер с пробросом порта 3000.. Если ничего нет — просто ничего не делает.

## Scoring ai-agent

Микросервис контекстного скоринга уязвимостей (SAST) на основе топологии сетевого графа микросервисов (`NetworkX`) и больших языковых моделей (`LLM`).

Сервис фильтрует ложные срабатывания (*False Positives*), обогащает находки статического анализа топологическим контекстом (внешняя доступность, кратчайший путь до интернет-шлюзов, близость к базам данных и хранилищам секретов) и формирует приоритизированную очередь объектов `VLSObject` для динамической верификации агентом-пентестером (DAST).

---

- **Язык**: Python 3.14
- **Пакетный менеджер / Сборщик**: Astral `uv` (`pyproject.toml` workspace)
- **API фреймворк**: FastAPI + Uvicorn
- **Топологический анализ**: NetworkX
- **Валидация схем**: Pydantic v2
- **LLM Интеграция**: OpenAI API (Structured Outputs / JSON Schema)
- **Контейнеризация**: Docker (Multi-stage uv build) & Docker Compose

## Архитектурная логика пайплайна

1. **Топологический анализ (`graph_tools.py`)**:
   - Построение направленного графа инфраструктуры через `networkx.DiGraph`.
   - Определение внешней доступности (`is_exposed`, расчет кратчайшего пути от шлюзов `gateway`).
   - Расчет метрик центральности (`betweenness_centrality`, `degree_centrality`).
   - Идентификация достижимости критических активов (`vault`, `database`, `auth`).
2. **Семантическая верификация (`agent.py`)**:
   - Оценка исходного кода на предмет санитизации и экранирования.
   - Детекция ложных срабатываний (`is_false_positive`).
   - Корректировка CVSS-балла с учетом графовых метрик (хопы, изоляция, blast radius).
   - Извлечение сетевых координат уязвимости (`endpoint`, `method`, `param`).
   - Формирование верификационной гипотезы для пентест-агента.
3. **Формирование очереди верификации**:
   - Отсев находок ниже `SCORE_THRESHOLD` в массив `discarded`.
   - Ранжирование очереди `queue` по убыванию итогового контекстного скора.
