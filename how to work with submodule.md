После клонирования этого репо вы скорее всего сможете увидеть пустую дерикторию project_docs – она не пустая, это гит-сабмодуль, ссылающийся на Ochre-Wormwood.  Это значит, что данный репо использует другой репо как вложение, что требует чуть-чуть нестандартной работы с гитом.

## 1. Клонирование репозитория с субмодулями
Если вы просто выполните git clone, папки субмодулей останутся пустыми. Скачать проект вместе со всеми зависимостями в один шаг можно с помощью флага --recurse-submodules:
```
git clone --recurse-submodules https://github.com/user/project.git
```
Если вы уже клонировали проект без этого флага, инициализируйте и обновите субмодули вручную: [4] 
```
git submodule update --init --recursive
```
## 2. Обновление кода субмодуля

* Синхронизация с удаленным репозиторием: Если в оригинальном репозитории сабмодуля вышли новые коммиты, подтяните их командой:
```
git submodule update --remote
```
* Получение изменений от коллег: Если ваш коллега обновил ссылку на субмодуль в родительском репозитории, после выполнения git pull вам нужно синхронизировать код локально:
```
git submodule update
```
# Основные комманды
Когда вы работаете с репозиторием, в котором есть субмодули, привычные команды (git pull, git switch, git commit) ведут себя иначе. Главное правило: родительский репозиторий и субмодуль — это два изолированных мира, и команды в корне проекта автоматически не управляют файлами внутри субмодуля.
Вот как именно они работают и какие флаги нужно добавлять, чтобы не сломать проект.

Git-субмодули (submodules) позволяют встраивать один Git-репозиторий в другой как отдельный подкаталог. Это незаменимый инструмент, когда вашему проекту требуется внешний код, библиотека или общие компоненты, но при этом историю коммитов и разработку этих зависимостей нужно вести изолированно. [1, 2] 
Главное, что нужно помнить: родительский репозиторий не хранит файлы субмодуля, он хранит лишь ссылку на конкретный коммит (SHA-1) внешнего репозитория. Это гарантирует стабильность вашей сборки. [3, 4]
------------------------------
## 1. git checkout / git switch (Переключение веток)
Когда вы переключаете ветку в основном проекте, Git меняет указатель на коммит субмодуля, но не обновляет файлы в самой папке субмодуля автоматически.

* Проблема: Вы переключились на ветку feature. В этой ветке субмодуль должен быть на коммите A. Но в вашей рабочей директории файлы субмодуля всё ещё остаются на старом коммите B. git status покажет, что субмодуль изменен (modified).
* Правильное решение: После каждого переключения веток в корне проекта нужно синхронизировать файлы субмодулей:
```
git submodule update --init --recursive
```
* Лайфхак: Чтобы Git делал это сам при каждом переключении, используйте флаг --recurse-submodules:
```
git switch --recurse-submodules feature_branch 
#или для старого синтаксиса: git checkout --recurse-submodules feature_branch
```

------------------------------
## 2. git pull / git fetch (Получение обновлений)
Обычный git pull в корне проекта стягивает изменения основного репозитория. Если ваш коллега обновил субмодуль (сдвинул указатель на новый коммит), вы получите этот новый указатель, но файлы в папке субмодуля останутся старыми.

* Проблема: Снова возникает ситуация, когда git status кричит, что субмодуль изменен, хотя вы лично ничего в нем не трогали.
* Правильное решение: Подтянуть код для самих субмодулей после пулла:
```
git pull
git submodule update --init --recursive
```
* Лайфхак: Делать это в одну команду:
```
git pull --recurse-submodules
```

------------------------------
## 3. git commit (Фиксация изменений)
Здесь важно понимать, что именно вы коммитите.

* Если вы изменили код внутри субмодуля:
1. Сначала вам нужно зайти в папку субмодуля (cd project_docs).
   2. Сделать коммит и обязательно сделать push там:
   ```
   git commit -m ""
   git push origin
   ```
   * Если вы коммитите в основном репозитории:
Когда вы возвращаетесь в корень (cd ..) и делаете git commit, вы коммитите не файлы субмодуля, а новую ссылку (SHA-1 коммита) на него.
* Лайфхак: Чтобы случайно не закоммитить ссылку на незапушенный код субмодуля (иначе у коллег всё сломается), при пуше основного проекта используйте защиту:
```   
   git push --recurse-submodules=check
   ```
   Git выдаст ошибку и не даст запушить основной проект, если вы забыли сделать push внутри субмодуля.

------------------------------
## 4. git status (Проверка состояния)
В корневом репозитории git status может показывать субмодуль в двух состояниях:
```
   1. modified: project_docs (new commits) — это значит, что в субмодуле появились новые коммиты (вы их сделали или скачали), но основной проект их ещё не зафиксировал.
   2. modified: project_docs (modified content) — это значит, что внутри субмодуля есть незакоммиченные файлы (грязный рабочий каталог).
```
Чтобы увидеть детальную разницу по субмодулям прямо из корня, используйте:

```
git diff --submodule
```

## Как автоматизировать это раз и навсегда?
Чтобы постоянно не писать флаг --recurse-submodules, можно настроить Git глобально:
``` 
# Чтобы git checkout/switch автоматически обновлял субмодули
git config --global submodule.recurse true
# Чтобы git pull всегда подтягивал код субмодулей
git config --global pull.rebase false # или true, по вашему вкусу
git config --global push.recurseSubmodules check
```
